# I-044A verification sandbox overlay

This digest-gated overlay extends the installed I-044B foundation without
executing checkout-local code as root. The worker creates a snapshot from one
fixed systemd `BindReadOnlyPaths` source. Clients cannot supply a path, digest,
or descriptor. A 256-bit server capability is single-use, expires after two
seconds, is bound to the preparing peer PID, and starts only that server-created
snapshot. The sandbox executes only the release-owned probe at
`/runtime/i044a_probe.py`; `/source` is untrusted read-only data.

The x86_64 seccomp program allows ordinary `clone` child creation but returns
`EPERM` when any known `CLONE_NEW*` bit is present. `clone3` is denied outright,
and an unexpected architecture is killed. The installed kernel acceptance reads
only the root-owned mode-0444 installed `seccomp.bpf`, verifies its digest against
the installed manifest, and verifies that manifest against the root-owned
release metadata. In one unchanged test process it reuses the same ordinary `clone3`
argument object: the call succeeds and its child is completely reaped immediately
before the exact installed filter is loaded, then returns `EPERM` immediately
afterward. The observed `Seccomp_filters` count increases by exactly one. This
same-process pre/post result attributes the denial to that newly loaded filter,
not to capabilities, namespaces, UID/GID, cwd, rlimits, or another process state.
Ordinary `clone` and `fork` remain allowed, while user, mount, and network
namespace attempts through both `clone` and `clone3` return `EPERM`.

`tests/test_i044a_seccomp_staging.py` is a separate non-installed staging test.
It may load the deterministic policy generated by the checkout installer, but it
does not claim installed acceptance. `tests/test_i044a_seccomp_kernel.py` has no
checkout import, generation fallback, repository policy source, or alternate
policy path; missing installed policy or manifest data is an acceptance failure.

Installed acceptance invokes only the release-owned client at
`/opt/novalton-verification/i044a-v2/client/i044a_client.py`. That restricted
client accepts no workspace or host path. The root-owned acceptance harness
independently hashes the live repository only to compare it with the digest of
the worker-created snapshot; no module or source file from the checkout is
imported or executed.

## Closed-world client operations

The CLI is structurally split between actions with no additional identity and
actions bound to one run identity:

```text
i044a_client.py <installed-manifest-sha256> <health|security|start|verify>
i044a_client.py <installed-manifest-sha256> <cancel|cleanup|result> <run-id>
```

Raw JSON, workspace paths, directory descriptors, mount selectors, and snapshot
selectors are not accepted on the CLI. Every operation first validates the
release identity through `health`; malformed release or run identities fail
before the requested operation is sent.

| Client operation | Workspace identity needed | Filesystem traversal | Trusted side | IPC fields | Checkout authority exposed |
| --- | --- | --- | --- | --- | --- |
| `health` | No | None | Worker reports fixed release state | `op` only | No |
| `verify` | Yes, as a trusted snapshot identity | Worker traverses only the fixed read-only bind; client traverses nothing | Worker creates, hashes, and consumes the snapshot | `prepare`; capability; run ID; worker source digest | No |
| `start` | Yes, as a trusted snapshot identity | Same worker-only traversal as `verify` | Worker | Same prepare/capability exchange, without client polling | No |
| `security` | No live-workspace identity; it exercises capability and descriptor rejection | No checkout traversal; anonymous pipes are used for rejected-FD probes | Worker owns any snapshot created by the successful prepare | Fixed negative requests, capability, and run ID | No |
| `result` | No; only an existing run identity | None | Worker | Validated run ID | No |
| `cancel` | No; only an existing run identity | None | Worker | Validated run ID | No |
| `cleanup` | No; only an existing run identity | None | Worker | Validated run ID | No |

The worker protocol's legacy `diagnostic` request is not exposed by this client.
For `verify`, the client requires the terminal result's run ID and source digest
to match the worker-issued prepare response. The provider-free contract test
stages a trusted static fixture with the production snapshot code, changes the
fixture after staging, and proves the live digest no longer matches the
snapshot digest. Installed acceptance performs no writes in, and accepts no
path to, the caller's checkout. Snapshot creation and selection remain
server-owned and the restricted client never gains repository traversal.

```text
root handoff SHA-256:       863b8d136687d60ff5b0de98e7a0d3c25773a86360052c8e919a71778f2af6e2
immutable installer SHA-256: c07f7318290167e81cab04c644c660e58deb97d678d677b99e9e1f41597dd507
bundle SHA-256:             762a34443398a5447ad27c3c4086569bad4a53c71bbec3983b7c6f267252e0a1
I-044A input SHA-256:       4753f65945be395b12ad2580862480b64e3cdf6945b40794b7b9679c06199d4c
foundation input SHA-256:   e71384ecc08842c6f6b65148463d6096d25cda24371c53877f35cd69f681c562
```

The two generations and the two installed proofs are deliberately distinct.
`foundation_input_sha256` and `i044a_input_sha256` identify reviewed inputs.
`foundation_installed_manifest_sha256` and `installed_manifest_sha256` identify
the actual root-owned installed bytes. The latter values may vary when the
compiler/toolchain changes; `release-metadata.json` binds all four values and
the worker validates the complete installed closure before serving IPC. The
historical I-044A installed digest
`935319e8d43272f8e325832c3bc9e382499a6b0f40abb71eedb9410217f273a8`
is retained only as evidence of the pre-migration host release.

The target update is a closed-set, sibling-directory promotion. Before touching
an existing target, the installer requires a real root-owned directory with a
complete root-owned mode-locked manifest closure whose digest is exactly either
the approved predecessor or this candidate. Any other pre-existing target,
including a symlink, drifted release, or unknown release, fails closed. It
first verifies the deterministic input generations and the concrete candidate
installed identity, then classifies
the installed target before selecting one exact authoritative unit: the bundled
candidate unit for an exact candidate target, the unit inside the verified
predecessor closure for an exact predecessor target, or the verified I-044B
unit for an absent target. An exact candidate is therefore checked active and
returned idempotently without materialization or mutation. For an upgrade or
fresh install, it builds and verifies the complete candidate in a root-owned
sibling first; only then does it stop the service, rename the approved
predecessor to a private sibling backup, promote the verified candidate, replace
the exact reviewed unit, reload, start, and verify active state plus final
release identity. A failure after the service stop restores the predecessor
directory and previous exact unit, reloads, starts, verifies it, and preserves
the failed candidate sibling for diagnosis. The predecessor backup is retained
after a successful promotion, so recovery is not dependent on in-place mutation
or a deleted old release.
Every stop invocation is treated as potentially state-changing even if
`systemctl stop` returns an error: before any predecessor move, recovery only
revalidates the unchanged target and exact unit, then starts and verifies the
predecessor. A rollback may use the sibling backup only after the predecessor
rename completed and that backup has independently revalidated as the approved
predecessor; a merely reserved pathname is never treated as a backup.

## Non-root review and preparation

From the repository root, verify the three handoff inputs without privilege:

```bash
sha256sum -c <<'EOF'
863b8d136687d60ff5b0de98e7a0d3c25773a86360052c8e919a71778f2af6e2  infra/verification/i044a-v2/root-handoff.sh
c07f7318290167e81cab04c644c660e58deb97d678d677b99e9e1f41597dd507  infra/verification/i044a-v2/install.py
762a34443398a5447ad27c3c4086569bad4a53c71bbec3983b7c6f267252e0a1  infra/verification/i044a-v2/bundle.tar
EOF
```

The provider-free source/bundle contract suite and separate staging kernel
proof must run without privilege before installation. The contract suite needs
the complete source/bundle tree and is not an installed acceptance command for
the partial `/run` stage. The kernel proof explicitly identifies itself as
staging rather than installed acceptance:

```bash
python3 infra/verification/i044a-v2/tests/test_i044a_contract.py -v
python3 infra/verification/i044a-v2/tests/test_i044a_seccomp_staging.py -v
```

The GitHub Actions validation workflow constructs new root-owned `/run` input
and reviewed stages, independently pins the handoff, installer, and bundle, and
only then interprets the copied stage. It never executes checkout-local Python
as root.

The checkout-local `install.py`, handoff, tests, and probe are never executed as
root. Only independently hash-verified root-owned `/run` copies are interpreted.

## Post-install acceptance

The handoff extracts the manifest-pinned acceptance scripts into the same
root-owned `/run` stage. The installed kernel test fails if the I-044A release,
manifest, or policy is missing or has the wrong type, ownership, mode, or digest.
Run it only after the reviewed release is actually installed, using the installed
immutable runtime:

```bash
sudo /opt/novalton-verification/i044a-v2/rootfs/runtime/bin/python3.13 -I -S -B /run/novalton-i044a-v2-reviewed/tests/test_i044a_seccomp_kernel.py
sudo /opt/novalton-verification/i044a-v2/rootfs/runtime/bin/python3.13 -I -S -B /run/novalton-i044a-v2-reviewed/tests/accept_i044a_installed.py
```

Do not declare `SANDBOX_READY`, commit, or push until installed acceptance passes
and the complete change receives independent security review.
